1The idea

What are we building, and why?

A store wants to know two things: what happened in its sales, and what will probably happen next. RetailAI takes real sales data, cleans it, explains it, and predicts how many units of each product will sell in the next 28 days.

  • Data: the public Kaggle M5 dataset (Walmart sales). We start small: one store and 20–50 products.
  • Tools: Python, CrewAI (AI agents), scikit-learn (machine learning), Streamlit (the app).
  • Team: two developers, working with Claude Code, one small reviewed step at a time.
Golden rule: normal Python code does all the math. The AI agents decide what to run, read the results, and explain them in words. They never invent numbers.

The whole chain is run by a CrewAI Flow: it hands results from one step to the next, logs everything, and stops safely if a check fails.

3Data and forecasting

How we predict the next 28 days without cheating.

Preparing the data

  • M5 stores sales in a very wide table (one column per day). We turn it into a normal long table: one row per day, store and product.
  • We add the calendar (events, holidays, SNAP days) and weekly prices.
  • We write a dataset contract: a file that says what columns and values are allowed. Team 2 must follow it.

Predicting

  • Baseline: "Seasonal Naive", just repeat what happened one week earlier. Any real model must beat it.
  • Two models: Ridge Regression and Random Forest (proposed; both from scikit-learn).
  • Scores: MAE and RMSE, on the last 28 days of history, which the models never see while learning.
  • No random shuffling. Time always goes forward: train, then validate, then test.

The "no cheating" problem

When predicting day 20 ahead, we do not yet know the sales of day 19. So we only use information that really exists at forecast time: calendar facts, and sales from at least 28 days earlier. Prices are left out of the model because future prices are unknown. These rules are checked by automatic tests.

Honest limits: M5 has no promotion or discount field, so we never claim "this discount caused more sales". Some products sell rarely, which makes them hard to predict. There is no stock or cost data.

4Optional parts (only if time allows)

The required project works fully without any of these.

PartWhat it isKey rules
RAG + Agent 7 OPTIONAL 3–5 short synthetic policy documents (promotion policy, discount limits, seasonality). Agent 7 searches them and quotes what it finds. Never invent a source or a discount percentage. If there is no evidence, say so. Ignore instructions hidden inside documents. About 4–6 hours of work.
Supabase OPTIONAL A cloud database that stores run history, predictions and insights, so the app can show old runs. The app must run without it. All storage goes through a Repository layer (LocalRepository first, SupabaseRepository later). Retrying never creates duplicates. Secret keys never go in Git.
Promotion analysis OPTIONAL Describe how price changes and sales move together. Description only. No causal claims.

If we run late, we cut in this order: Supabase, then Agent 7/RAG, then promotion analysis. We never cut the required Flow, files or forecasts.

5The app (Streamlit)

Simple screens, clear information.

  • Home: start a run and see its status.
  • Data Quality: what was checked and what was fixed.
  • EDA and Business Insights: charts and findings.
  • Sales Forecast: pick a product, see history plus the next 28 days.
  • Model Evaluation: MAE/RMSE for each model, per product.
  • Recommendations OPTIONAL: advice, sources and limits.
  • Run History and Logs: past runs and any errors.

7How we work in Git

Repository: micgotler-cmd/retailai-multi-agent-sales-intelligence (public on GitHub).

main
stable, the "finished" version. Only changed by a Pull Request from dev.
dev
where work comes together and gets tested.
feature/…
one branch per task, made from dev, e.g. feature/analyst-crew.
  1. Create a feature branch from dev.
  2. Build it and write tests.
  3. Update docs/progress.md.
  4. Open a Pull Request into dev; the other developer reviews it.
  5. Merge. At a stable milestone, open a Pull Request from dev into main.

Safety checks at every phase change

Before moving to the next phase we run (1) a security review and (2) the end-to-end test. Both must pass first.

Never commit

Passwords or API keys (.env), the Kaggle dataset, trained models, vector databases, or big generated files. GitHub rules already block force-pushes and deleting main/dev, and require a Pull Request.
